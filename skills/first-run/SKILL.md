---
name: first-run
description: Profile a repository's stack, commands, layout, integrations, conventions, and domain for the Essentials skills. Use once when adopting a project, after major stack changes, or after an Essentials profile-schema update.
---

Generate the project profile that tailors every Essentials skill to **this** codebase. Apply any scope or constraints from the user's prompt.

The skills are codebase-agnostic and can re-detect the stack on every run. This workflow does that detection **once**, deeply, and writes the result to `.codex/essentials-profile.md`, which repository-aware review, test, debugging, documentation, dependency, and orchestration skills read first. Run it once per project and again after a major stack change.

**If the profile already exists**, read it first, re-verify each line against the current repo, and update only what changed — preserve any lines the user added or edited by hand.

## Step 1 — Detect the codebase

Investigate thoroughly. When subagents are available, spawn one `explorer` subagent for a very thorough repository sweep while you confirm specifics in the main thread. Determine:

- **Stack** — language(s) + version, framework(s), runtime, package manager(s), database/data layer. For the data layer, note the access idiom and what a "no row found" lookup returns (`null`/`None`/`false`/empty/throws) — `$logic-review` keys off this.
- **Commands** — the exact `test`, `lint`, `typecheck`, `build`, and `run` invocations the project actually uses (from `package.json` scripts, `Makefile`, `justfile`, `pyproject.toml`, CI config). If there's a separate E2E suite (Playwright/Cypress/Selenium), record its command too. For `run`, note the local URL/port. Prefer real project scripts over generic guesses.
- **Git** — the default branch (from `git symbolic-ref -q --short refs/remotes/origin/HEAD`, or the branch CI targets). Review skills diff against it.
- **Layout** — where source lives, where tests live and their naming pattern, where migrations live (which tool, which database dialect), where routes are declared (explicit route table vs convention-based), the templating/styling approach, where docs live, and which dirs to **skip** (vendored, generated, build output, fixtures).
- **Integrations** — inbound webhook receivers (Stripe, GitHub, Twilio, custom HMAC…): provider and handler path, or "none".
- **Conventions** — hard rules the project states in `AGENTS.md`, `CONTRIBUTING`, lint/formatter config, or that are obvious from the code (e.g. "data access stays out of controllers", "no inline styles", error-handling idiom, the test framework + assertion style).
- **Domain** — 1–3 sentences on what the app does and its key entities, so reviewers judge behavior, not just syntax.

**Verify, don't guess.** For each command, confirm it actually exists (the script is defined, the binary is on PATH); where cheap, run it in a list/dry-run/`--version` form. Record only what you verified; mark anything uncertain as `(unconfirmed)` rather than guessing.

## Step 2 — Write the profile

Show the user the detected summary first. On confirmation, create `.codex/essentials-profile.md` (create `.codex/` if needed) using this structure. Fill every section and omit lines you couldn't determine:

```markdown
# Essentials project profile
<!-- Generated by $first-run on <date> at <short commit sha or "unborn">. profile-schema: 2. Read first by the Essentials skills. Edit freely — it's yours. -->

## Stack
- Language: …
- Framework: …
- Package manager: …
- Data layer: … ("no row found" returns: …)

## Commands
- Test: …
- Test (E2E): …
- Lint: …
- Typecheck: …
- Build: …
- Run: … (serves at: …)

## Git
- Default branch: …

## Layout
- Source: …
- Tests: … (pattern: …)
- Migrations: … (tool: …, database: …)
- Routes: … (style: explicit | convention-based)
- Templates/UI: …
- Docs: …
- Skip: …

## Integrations
- Webhooks: …

## Conventions
- …

## Domain
…
```

Omit any line that doesn't apply (no migrations, no webhooks, no E2E suite) rather than writing "none" everywhere — but keep `Webhooks: none` explicitly if you checked and found none, so `$webhook-review` can skip its search.

## Step 3 — Make it auto-load

So the main thread and non-Essentials tasks know the profile exists, maintain this exact managed block in the repository-root `AGENTS.md`. Create `AGENTS.md` if absent, append the block if missing, or replace only the existing block if it is stale. Preserve every line outside the markers.

```markdown
<!-- essentials:start -->
## Essentials project profile

Before repository review, testing, debugging, release, or quality work, read `.codex/essentials-profile.md` when it exists and treat it as the source of truth for this project's stack, verified commands, layout, integrations, conventions, and domain.
<!-- essentials:end -->
```

## Output

Confirm both files were updated, show their paths, and explain that all Essentials review, test, documentation, dependency, orchestration, and triage skills consume the profile. The opt-in run-tests-on-stop hook consumes its verified `Test` command only when `ESSENTIALS_USE_PROFILE_TEST_CMD=1`. Tell the user to re-run `$first-run` after a major stack change or a plugin update, or edit the profile directly.

> Keep the `profile-schema: 2` marker in the header comment exactly as written — the session-start hook uses it to detect profiles generated by older plugin versions. Bump it here and in `hooks/suggest-first-run.sh` together whenever the template gains or renames fields.
